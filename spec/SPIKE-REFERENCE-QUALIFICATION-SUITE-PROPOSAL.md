# Spike Report — public reference qualification suite

**Status: closed.** Run by Claude Sonnet 5 under Architect role, authorized by Scott Wofford, Change Owner, on 2026-10-06. Non-mergeable — this is a design answer, not code.

- **Question the spike answers:** The only qualification suite this repository ships (`profiles/qualification-eval/suite-v1.1.json`) is pinned to one private pilot's repository and revision; `qualification_check.py` rejects any profile whose repository doesn't exactly match it. No external adopter can run it. What domain, per-mode verification method, and known-good-disposition authoring process would let AIDF ship a real, runnable, public reference suite — and what classification does building it warrant?

- **Time-box:** Proposed one day; compressed to one session, since the running Architect already held the needed context (`modes/execution-modes.md`'s M0–M3 definitions, the qualification protocol's mandatory-case and evidence-jurisdiction rules, and direct reading of the existing private-pilot cases' actual shape, all from this session's own prior work).

- **What was tried:** Re-derived what a case must actually contain from the protocol itself rather than designing abstractly: cross-checked `modes/execution-modes.md`'s per-mode "Required output" and "Verification of its output" columns against the real structure of existing cases (`verification/phase7-qualification-execution-evidence/m0..m3/`) to find what a new case needs to supply versus what the schema/validator already handles. Evaluated candidate reference-app domains against four criteria: broad recognizability independent of an evaluator's own domain, genuine invariant/security depth (so M2/M3 cases mean something), small enough to build and maintain as a public artifact, and no overlap with the existing suite's private product so it doesn't just relocate the same narrowness in a new direction.

- **Findings:**
  1. **A case needs a verification method matching its mode's own definition, not just a prompt and an answer.** M0 needs a deterministic, mechanically-checkable transform (easy — any codemod works). M1 needs an evidence pack checkable against an already-accepted reference implementation or a test suite that only a correct implementation passes. M2's grading is inherently human/Architect judgment of a decision, not mechanizable — the protocol already defers this correctly (`modes/execution-modes.md`: "human or Architect review of the decision, not the prose") and a new suite should not pretend otherwise. M3 needs a **deliberately planted, known** defect or invariant violation, so "found it" has an objective ground truth, with the same "no manufactured findings" check the existing M3 cases already use.
  2. **The genuine bottleneck is authoring known-good ground truth independent of any candidate, not validator mechanism.** The private pilot's cases work because their ground truth already happened — real historical bugs and outcomes. A new reference app has no history to mine; its invariants and defects have to be deliberately authored, then independently proven findable/checkable (a real falsification attempt against each planted M3 defect, before it's trusted) before the case is accepted into the suite. The schema and validator (`qualification_check.py`) need no changes — this is new authored content and a new small review step, not new engineering.
  3. **A small multi-tenant SaaS backend satisfies all four domain criteria.** Auth, role-based permissions, and tenant data isolation give genuine invariants worth violating for M2/M3 (a cross-tenant data leak, a negative-balance edge case) without requiring firewall/network domain knowledge; M0/M1 work (codemods, a feature built to an established contract) fits naturally on top of it; it is small enough to build and maintain as a public fixture tree; and it shares no product identity with the existing private suite.
  4. **The domain choice mechanically forces T3, and that is correct, not a surprise to route around.** `verification/policy.json`'s tripwire family `authentication-authorization-session-permissions` matches `**/auth/**` and `**/permissions/**` by path. A reference app whose own source tree plausibly contains directories named `auth/` or `permissions/` will trip this the same blunt, intentional way `profiles/authorization/**` already has twice this session. This is genuinely security-relevant work — errors in a public trust-mechanism reference would quietly undermine the qualification story for every future adopter — so the mechanical signal and the substance agree.

- **Blast radius / architectural impact discovered:** New content only — a self-contained reference-app fixture tree (proposed location: `profiles/qualification-eval/reference-app/`, embedded in this repository rather than a second standalone repo, so an adopter who clones AIDF can run the suite with nothing else to fetch) plus a new `suite_id`/`suite_sha256`-bearing suite file alongside the existing ones. Does not touch `modes/execution-modes.md`'s M0–M3 definitions, `core/`, `KERNEL.md`, or `qualification_check.py`'s validator logic. Does not rename, rewrite, or invalidate the existing private-pilot suite or any digest-bound evidence under `profiles/qualified/**` — the new suite is additive, not a replacement.

- **Resulting Spec Confidence:** Clear, conditional on three proposed defaults the Change Owner should confirm rather than treat as already decided: (a) embedded fixture tree, not a second repository; (b) a per-mode mandatory-case count similar in scale to the existing suite (current real counts: 4 for M0, 10 for M1, 3 for M2, 4 for M3) rather than an open-ended target; (c) defects/invariants authored by an AI instance under Architect role, each independently proven via a real falsification attempt, with explicit Change Owner review and acceptance before the suite is trusted — mirroring the existing protocol's own reviewer-attestation requirements rather than inventing a new acceptance process.

- **Resulting classification recommendation:** **T3.** Both because the tripwire family will mechanically fire on the chosen domain's own file paths (finding 4), and substantively: this is net-new content load-bearing on the entire Layer 2 trust mechanism, not a bounded, reversible change.

- **Next step:** Proceed to Task Contract (T3), scoped to the fixture tree and new suite file described in "blast radius," with the three proposed defaults above written into its acceptance criteria explicitly rather than left implicit, and the Change Owner's confirmation or amendment of each obtained before implementation begins.

- **Branch:** None cut — investigation was conducted by direct analysis against `origin/main`, no throwaway code produced.
