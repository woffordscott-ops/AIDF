# Task Contract: Spec-Tool Bake-off, Stages 0 and 1 (paper protocol and headless probe)

`core/01-lifecycle.md` §4. Class T2 (see Classification); Approved status required from a human under Architect authority before implementation begins. **Status: Approved by the Change Owner on 2026-11-05 (see Status).** It implements stages 0 and 1 of `strategy/AIDF-SPEC-TOOL-BAKEOFF-PROPOSAL.md` (merged to main as `473c4b5`, decisions accepted 2026-11-05).

## Why (the evidence)

1. **The proposal makes every later stage depend on two facts nobody has checked.** Stage 0 asks whether a spec tool can save the human anything once approval and review stay in every arm; stage 1 asks whether either tool can be driven headless at all. Both are cheap to answer and either can end the effort before 120 scored runs and a harness change.
2. **The READMEs say little the bake-off needs.** A fact check on 2026-11-05 (Spec Kit v1.3.0, OpenSpec v1.16.0) found no statement about risk, approval, evidence or headless use in either, no pin command, and the apply step (`/speckit-implement`, `/opsx:apply`) as an unguarded agent command. Stage 1 therefore has to observe what a run writes, and when.
3. **The measurement harness runs candidates that cannot be seen mid-turn.** `verification/aidf-measurement-round/run_round.py` calls `cursor-agent -p --trust` and reads the workspace afterwards; "approval" in Arm A is the boundary between the contract turn and the implementation turn. The bake-off's mutation log needs a record of what changed in the workspace at that boundary. Stage 1 builds and tests that snapshot-and-compare as a small separate tool, so stage 2 can reuse it, and does not touch the harness.

**Why two contracts, not one for stages 0 to 2:** what stage 2 must contain (the mapping fields, the arm prompts, how writes are logged) is not known until stages 0 and 1 have run, and an approved contract may not be edited afterwards without asking. A contract for stage 2 is written after the Change Owner's decision at the stage 1 gate.

## Part A: Minimal

- **Intended outcome:** The Change Owner can decide, from evidence and before any scored run, whether the bake-off goes on: a written protocol and field-level mapping with the human steps counted for each arm, the observed behaviour of both tools under a headless agent, and a tested snapshot tool that records what a run writes and when. No scored case is run and no existing harness file changes.
- **Acceptance criteria:**
  1. **Pinned inputs.** The stage 0 document (`strategy/AIDF-SPEC-TOOL-BAKEOFF-STAGE0.md`) records, for Spec Kit and OpenSpec: the release tag, the commit it points to, the SHA-256 of the README read, the licence, and how the install is pinned (not `@latest`). The extraction of the READMEs (2026-11-05) is committed as `verification/spec-tool-bakeoff/inputs/readme-extraction-2026-11-05.md` with the two README hashes in its header.
  2. **Protocols and step count.** For A0, A1 and A2 the document lists each step in order with who acts (human, agent, script) and what it produces, and counts the human steps. Any saving of A1 or A2 against A0 is explained by naming the step that is deleted, merged or moved; if none is, it says so.
  3. **Field-level mapping.** A table of every Task Contract field (from `templates/task-contract.md` and the JSON schema) against A1 and A2: supplied by a named tool artifact and section, supplied partly (what is missing), or AIDF-only. It states the AIDF-only count per arm and where Spec Kit's constitution maps or whether it is AIDF-only.
  4. **Stop rule and verdict.** Before the table is written the document states the stop rule: stop if no saving remains that leaves approval and review in place, or if more than half of the contract fields are AIDF-only for a tool. It then gives a verdict per tool (continue, stop, or needs the Change Owner's decision) with the reasons. The verdict is advice; the gate decision is the Change Owner's, recorded in the dispositions file.
  5. **Snapshot tool.** `verification/workspace_snapshot.py` takes a directory and writes a record of every file (relative path, size, SHA-256, mtime), compares two records and reports added, removed and changed paths, and redacts the absolute path of the machine in what it writes. It follows no symbolic link out of the directory, skips a named exclude list (`.git`), and never writes inside the directory it records. Tests: added, removed, changed, unchanged, a link pointing outside, an excluded name, redaction, and a record taken twice compares equal.
  6. **Headless probe.** `verification/spec_tool_probe.py` runs one probe per tool in a scratch workspace outside the repository: installs the pinned version into a scratch prefix (no global install, no change to the account's configuration), sets the tool's telemetry off, takes a snapshot, runs `cursor-agent -p` on a throwaway prompt with a stop before the apply step, takes a snapshot after each turn, and writes a JSON record (versions, commands run, exit codes, durations, snapshots compared, the agent's reply). The throwaway prompt names no case of any suite. The record's local paths are redacted. A `--dry-run` prints the plan and runs nothing.
  7. **What the probe must answer, with evidence in the record.** (a) Does the pinned install work without a global change? (b) What does init write (folders, agent command files, hooks, configuration)? (c) Does `cursor-agent -p` run the tool's propose/specify/plan/tasks flow, by command or by the command file's text? (d) What does each turn write, and does a stop before the apply step hold? (e) Is telemetry off? (f) Time per turn and the number of agent calls. A question that cannot be answered is recorded as "not answered" with the reason.
  8. **Safety of the probe.** Where the agent can write is stated before the run (decision 3). The environment passed to a child is an allowlist; no credential of the account is passed except what `cursor-agent` needs to run; nothing is written under the repository by a probe except its redacted record.
  9. **Proposal corrections.** `strategy/AIDF-SPEC-TOOL-BAKEOFF-PROPOSAL.md` gains: Spec Kit's `/speckit-converge` and the bug and assessment extensions; "delta" removed from the OpenSpec description; the pins; the OpenSpec telemetry setting; and the contract split above. Nothing else in it changes, except the outcome paragraph recording that the bake-off was stopped after stage 1 and the correction of the sentences that the outcome made stale (amended 2026-11-05, see the end of the Status).
  10. **Tests and checks.** The new modules have tests that fail without them; the whole suite passes on Windows, under WSL and with SIGINT ignored; the preflight (`--ci-like`), ruff and `mypy --strict` pass on the new files; the public-tree scan passes.
  11. **Scope.** No change to `verification/aidf_measurement.py`, `verification/aidf-measurement-round*`, the qualification suite, its cases, the reference application, the preflight, `core/`, `verification/aidf_check.py` or any approved contract. No scored run, no stage 2 file (mapping script, arm prompts, pre-registration). Nothing is published.
  12. **Outcome records** (core/05-review.md section 6): the review report patterns are `verification/spec-tool-bakeoff-stages-0-1-verifier-report*.md`; the dispositions file is `verification/spec-tool-bakeoff-stages-0-1-verifier-dispositions.md`. This criterion only declares the outcome-record paths.
  13. **Reading test (added 2026-11-05 at the gate, option D).** The probe gains a mode `aidf` (no tool; the framework documents are copied into the workspace and the agent writes a Task Contract), the options `--sample`, `--change-file` and `--collect`, and its tests. For one throwaway T2-class change in a small sample project under `verification/spec-tool-bakeoff/reading-sample/`, one run each of A0 (AIDF-native), OpenSpec and Spec Kit produces the planning artifacts, collected and redacted under `verification/spec-tool-bakeoff/reading-test/`, with a reading form. The Change Owner reads the three sets as if approving the change before implementation, in an order set by the Implementer, and times himself; his times and answers are recorded in the dispositions file. The result informs the stage 2 decision and is not a measurement (one change, one reader, one run per arm). A second round (option E, added 2026-11-05) repeats the AIDF-native arm once on the same change with an extra instruction in the prompt asking for a short "read first" opening (the problem, what changes with any behaviour change for existing callers named, scope, what is tested); the probe gains `--prompt-extra`. The Change Owner reads the new contract with the same form. `templates/task-contract.md` is not changed by this contract.

## Part B: Plan

- **Approach:** Stage 0 first, as a document, then the verdict. The snapshot tool next (pure, tested). The probe script is the thin layer that installs, runs the agent and calls the snapshot tool. The probe runs only if stage 0 does not already stop a tool, and only after the Change Owner's go for the run (it uses reviewer-class quota and installs third-party software in a scratch area).
- **Invariants touched:** none of the repository's gates. New behaviour: running third-party tools and a write-capable agent in a scratch workspace.
- **Evidence strategy:** the stage 0 tables are checked against the pinned READMEs; the snapshot tool by tests and mutation of each comparison branch; the probe by a dry run, tests of its pure parts (command building, environment allowlist, redaction), and the two real runs whose records are committed.
- **Review budget (this change):** one preflight run and two Verifier rounds; a third needs the Change Owner's recorded reason and a rank-1 finding. No pre-authorisation of four here: that belongs to the stage 2 harness contract. Accepted limits stated before review: two probe runs show what happened once, not what always happens; a different `cursor-agent` version may behave differently; the probe cannot prove a tool never writes before approval.
- **Protected files touched:** none.
- **Recovery / reversal approach:** `git revert`; a probe leaves only its scratch workspace and prefix, which are deleted after the record is made.

## Classification

Proposed **T2**: it adds tooling and documents with no trip-wire in the repository. **No trip-wire in the repository applies, and no third-party dependency enters it** (the two tools are installed only into a scratch prefix and are not imported by any repository file). Because the kernel gate says a new third-party dependency needs human approval regardless of class, the Change Owner's approval of this contract is asked to cover the scratch install of the two pinned tools by the probe, nothing wider.

## Decisions for the Change Owner

1. **One contract or two?** Two [recommended: this one for stages 0 and 1, a second for stage 2 after the gate], or one covering stages 0 to 2 now (it would have to be amended after the gate).
2. **Which tools does the probe run?** Both Spec Kit v1.3.0 and OpenSpec v1.16.0 [recommended], or one.
3. **Where may the agent write during the probe?** (a) WSL with the CLI's sandbox, if `cursor-agent` runs there [recommended; the sandbox works only on macOS and Linux], else (b) Windows in a scratch directory outside the repository with an allowlisted environment and no sandbox, disclosed in the record as in the earlier rounds.
4. **Stop-rule number.** "More than half of the contract fields are AIDF-only" [recommended], or another threshold.
5. **Review layers:** Verifier rounds only [recommended], or add the security layer for the probe script.
