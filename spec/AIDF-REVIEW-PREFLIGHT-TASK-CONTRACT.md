## Part A: Minimal

- **Intended outcome:** A change reaches its first review with the avoidable failures already removed, and the review brief stops being rebuilt by hand each round. In `review-efficiency-core` five of the avoidable failures were found by a reviewer or by CI instead of by the Implementer: a mypy error CI runs and the Implementer did not (round 1); a new checker never run over the existing records it must accept (rounds 2 and 3); an edit to a file attested by the protected policy repository, which failed `aidf-governance` after the last review and forced a split and a fifth round.
- **Acceptance criteria:**
  1. **Preflight.** `verification/preflight.py` (Python, so it runs on Windows and POSIX) runs, in a clean checkout of a committed head, the commands of the pipeline jobs `checker-fixtures` and `static-analysis` and the ordinary governance commands (criterion 2) plus this change's contract, evidence, scope, trip-wire, public-tree and pack-facts checks, prints one line per step, and exits non-zero if any fails. It diffs against the tip of `origin/main`, as the pipeline does, and fails if that tip is not an ancestor of the head. It refuses to run on uncommitted tracked changes. It does not replace CI and is not a security control.
  2. **Commands come from the policy.** The pipeline that enforces is defined in the protected policy repository (`aidf-enforced.template.yml`); this repository's `.gitlab-ci.yml` is not imported by it. When the policy repository is reachable the preflight runs, instead of a list kept here, the single-line `python3`, `ruff` and `mypy` commands of the jobs `checker-fixtures` and `static-analysis` at the same ref (`python3` runs as the current interpreter; other lines, such as package installation and version assertions, are printed as skipped; only those three leading words are run). It then runs the governance commands `exemptions`, `secrets` and `test-delta` of the job `aidf-governance`, and prints a warning naming any other `aidf_check.py` subcommand that job runs for an ordinary head and that the preflight does not. With `--offline` it runs a built-in list and says plainly that the list may not match the pipeline.
  3. **Protected files, by lookup.** The preflight reproduces the attestation check of the policy repository instead of keeping a list: it fetches the policy repository (default: the sibling `aidf-ci-policy` of the `origin` remote, or `--policy-repo`; at `--policy-ref`, a full commit SHA, default the head of its `main`, printed with a warning that the SHA in the consuming project's CI/CD setting is the authority and may differ), reads the `records` of its `aidf-enforced.template.yml` (the files attested for every head: `verification/aidf_check.py` and `verification/policy.json` at the time of writing), takes the expected SHA-256 from the matching file under `trusted/` with line endings normalised as `build_policy.py` does, and compares it with the SHA-256 of the file at the head under test. A mismatch names the file and says that the change needs a cross-repository T3 change to the attestation; it fails unless `--allow-protected <reference>` names that change, and the reference is printed. A record variable the preflight does not recognise fails closed. The records that apply only to named historical candidate commits (phase 7, phase 8, layer 3) are not checked, and the preflight says so. If the policy repository cannot be reached the step prints `SKIPPED: policy repository unreachable` and the preflight exits non-zero unless `--offline` is given, so a skipped lookup is never read as a pass. `templates/task-contract.md` Part B gains the line "Protected files touched: none, or the paths and the T3 change that updates their attestation". (The JSON contract schema is checked by the attested `aidf_check.py`, so the field is not added to the JSON.)
  4. **New-rule checklist.** `templates/task-contract.md` Part B gains a checklist for a change that adds a rule or a checker: name the existing records it must still accept and run it over them before review; walk the rule through the lifecycle of the change that introduces it; search the locked documents for the limit it touches; do not edit an approved contract without asking; call a waiver a waiver.
  5. **Review brief.** `templates/review-brief.md` holds the standing lines used in the hand-written prompts of rounds 12 to 16: the pinned head and the delta since the last reviewed head, the preflight output attached, read-only commands only, "say plainly whether your shell worked", the section 4 record-text rule, the outcome words PASS, PASS_WITH_ADVISORIES and BLOCKED only, "list the routes you tried and found closed", the cap on non-blocking findings, and the instruction not to raise recorded Change Owner acceptances. It is a template to fill, not a generator.
  6. **Tests.** Each criterion has a test that fails without it: a temporary repository where a protected path is changed fails the preflight and passes with `--allow-protected`; an uncommitted tracked change is refused; command extraction from a policy template text yields the expected commands and skips any line that does not start with `python3`, `ruff` or `mypy`; a record variable it does not know fails closed; an unreachable policy repository exits non-zero unless `--offline` is given; the template fields are present (presence tests, stated as such). `mypy --strict` and `ruff` pass on the new file. `CHANGELOG.md` records the change as additive.
  7. **Scope.** No change to `verification/aidf_check.py`, `verification/phase2-task-contract.json`, `.gitlab-ci.yml`, `KERNEL.md`, trip-wires, `core/02-authority.md` or `core/05-review.md`.
  8. Outcome records (core/05-review.md section 6): the review report patterns are `verification/review-preflight-verifier-report*.md`; the dispositions file is `verification/review-preflight-verifier-dispositions.md`. This criterion only declares the paths.

## Part B: Plan

- **Approach:** Port `Projects/preflight.sh` (kept outside the repository during the previous change) to `verification/preflight.py`; add the policy lookup and the policy-derived command list; add the two template changes; write the brief template from the prompts of rounds 12 to 16.
- **Invariants touched:** none of the stable surface. The preflight is advisory to the Implementer and changes no review rule.
- **Evidence strategy:** counterfactual tests as in criterion 6. Replay: run the preflight at the heads that failed in `review-efficiency-core` (the round 1 head with the mypy error, the pipeline-failing head with the `aidf_check.py` edit) and show it fails there and passes at the final head. The replay uses heads recorded in the dispositions, not new data. The lookup is also run once against the real policy repository (`ProjectGenome/aidf-ci-policy` at the SHA printed by the run), and the result is recorded.
- **Review budget (this change):** one pre-check run with the preflight itself, two Verifier rounds. A third round needs the Change Owner's recorded reason and a rank-1 finding in code, tests or security posture. Accepted limits stated before review: the lookup needs SSH access to the policy repository and reads its `main` unless given a SHA, while the SHA in the project's CI/CD setting is the authority and the preflight cannot read that setting without a credential, which it will not take; the brief template has presence tests only; the preflight runs the local Python and tool versions, which may differ from the pipeline image.
- **Protected files touched:** none.
- **Recovery / reversal approach:** `git revert`; nothing depends on the new files.

## Classification

Proposed **T2**: a new verification tool in `verification/`, no kernel trip-wire. It reads git and runs local commands, takes no credentials and changes no control, so no Security Reviewer is proposed (the Change Owner may require one).

## Outline of 5b (not part of this contract)

`verification/run_review.py`: pin the head, build a clean checkout, fill the brief from the contract, run the reviewer CLI with credentials removed from its environment, save its answer verbatim, reject an outcome word outside the three, commit the report alone, and log start and end times. It handles credentials and runs a subprocess, so it should be T2 with a Security Reviewer, and it should come after 5a has produced a few records.
