# Task Contract — AIDF Benefit-versus-Burden Measurement

`core/01-lifecycle.md` §4. T2 — Part A and Part B; Approved status required from a human under Architect authority before implementation begins. **Status: Approved 2026-10-23; the open questions are resolved in Part B. Nothing is implemented yet.**

## Part A — Minimal

- **Intended outcome:** Produce a defensible, repeatable answer to one question: does working under AIDF reduce the defects that reach a merged result by more than it costs the people who adopt it? Today the repository has the framework, a public reference application with ground truth (`profiles/qualification-eval/reference-app/`, suite `suite-v2.json`, a 104-mutant catalogue in `tools/mutation_check.py`) and a design intention (`spec/AIDF-v1.2.2-design-proposal.md` §13.4, `strategy/PHASE8-PROCESS-VALIDATION.md` §13), but no measurement of benefit and no baseline for burden. This change defines the experiment, the metrics and the reporting format, and runs a first small round.
- **Acceptance criteria:**
  1. **Two arms, same tasks.** Each measured task is performed in two arms by the same model and tool: **Arm A** under AIDF (an approved task contract, an evidence pack, and the independent review that the task's class requires), **Arm B** as a plain baseline (the task text and the tests visible to the agent, no AIDF documents, no independent review; the agent's own checking is allowed and recorded). For M1 tasks a control **Arm C** is added: the baseline with the same number of visible-suite fix chances as Arm A can use, and no AIDF contract or review, so that the effect of AIDF's structure can be told from the effect of more attempts. The tasks are taken from the reference application's M1 implementation cases (positive cases with hidden tests) and its M3 review cases (planted defects), so ground truth is already authored and falsified. *(Design chosen by Scott Wofford, Change Owner, 2026-10-23: controlled A/B on planted-defect tasks.)*
  2. **Benefit metrics, from ground truth only.** Per arm and per task: (a) hidden-test pass or fail; (b) escaped defects: for an M1 case, the named hidden tests that the delivered result fails, each tied to one defect type of the case (the hidden tests and the case's `plausible_wrong_*.diff` files are the case's defect catalogue; the 104 mutants of `tools/mutation_check.py` target the base application and are not used); for an M3 case, the planted defects that the delivered review misses; (c) for M3 cases, planted defects found and false findings raised (finding precision, `spec/AIDF-v1.2.2-design-proposal.md` §11.5); (d) for M1 cases, whether the repository's own visible test suite passes at delivery, as the task text requires (added after the pilot and labelled post hoc wherever reported). The delivered-failure rule that combines these is fixed in `verification/aidf-measurement-preregistration.md`, committed before the full round. No benefit figure is derived from a reviewer's opinion alone.
  3. **Burden metrics, adopter-repeatable only.** Per arm and per task: elapsed time from task start to accepted result; number of review rounds and fix cycles; agent runtime and cost where the tool reports it; and the Change Owner's **decision points**, counted, not timed: the approvals the process requires of the Change Owner for the task's class (one for an AIDF T2 Task Contract, none otherwise), taken from the process rules; a subset of runs in which the Change Owner actually answers is reported separately. *(Scott's answers, 2026-10-23: count decision points, not minutes; judge adopter-repeatable cost only.)* One-time costs of building AIDF itself, and review loops caused only by wording of documentation about the framework, are excluded from the headline figure and **reported separately** so they are visible, not hidden.
  4. **Missing is not zero.** A metric that could not be recorded is `unknown` and the report says how many were unknown; it is never defaulted to 0 (`strategy/PHASE8-PROCESS-VALIDATION.md` §13).
  5. **Replication and honesty about size.** Each task runs in each arm **5** times with fresh sessions (at least 3); the report gives counts and ranges, states the sample size, and makes no significance claim the sample cannot support, and applies only the decision rules and burden tolerance written in `verification/aidf-measurement-preregistration.md` before the round. A result that favours neither arm, or favours the baseline, is reported as it is.
  6. **Fairness controls recorded.** The model, tool, prompts, tests visible to the candidate, time limit and number of attempts are identical across arms except for what AIDF adds; any difference is listed. The reference application's answer key is public, so the report states that candidates may have seen it and which arm each run's candidate identity belongs to.
  7. **Reproducible record.** Every run's inputs, the delivered result, the hidden-test and mutant outputs and the burden log are committed as evidence under `verification/aidf-measurement-*/`, with local paths removed at generation time; the summary table can be rebuilt from them by a script with no manual numbers.
  8. **Separation of duties.** The Arm A and Arm B candidates are not the instance that scores them, and the scorer does not know which arm produced a result when the scoring is a judgment (M3 findings); scoring that is a test or mutant run is mechanical.
  9. **Additive only.** No change to `core/`, `modes/`, `KERNEL.md`, any validator, the reference application, its cases or `suite-v2.json`. The measurement reads them; it does not alter them.
  10. **Report.** One committed report (`strategy/AIDF-BENEFIT-BURDEN-REPORT.md`, name provisional) with a single headline table (benefit per arm, burden per arm, both adopter-repeatable), a separate table of excluded costs, the limitations, and a plain statement of what the data does and does not support. The Change Owner accepts the report before it is cited.

  Spec Confidence: Clear. The design (A/B on planted-defect tasks, decision points not minutes, adopter-repeatable scope) and the three questions in Part B are settled by the Change Owner's replies recorded there.

- **Declared scope:** new `spec/` contract and, once approved, new `strategy/AIDF-BENEFIT-BURDEN-REPORT.md`; new `tools/` or `verification/` scripts for run orchestration, scoring and the summary table; new `verification/aidf-measurement-*/` evidence; tests for those scripts; narrow pointers in `README.md` and `IMPLEMENTATION-STATUS.md`. **Excluded:** everything in AC 9, `profiles/qualified/**`, `profiles/authorization/**`, and CI configuration.

## Part B — Plan

- **Approach:** Three steps, in order. (1) **Pilot** one M1 task and one M3 task, two runs per arm, to check that the metrics can be recorded and the arms are comparable; adjust the procedure, not the results. (2) **Full round** of the task set agreed after the pilot, at least 3 runs per task per arm. (3) **Report** per AC 10. Orchestration and scoring scripts are written and tested first so that the numbers come from code.
- **Why the reference application:** it already holds ground truth: hidden tests per M1 case, a mutant catalogue, and planted defects per M3 case, each independently falsified. That is the only part of this repository where benefit can be scored without opinion. It is small, so the result says something about AIDF on small, security-sensitive backend changes and not about every kind of work; the report states that.
- **Questions put to the Change Owner and their resolution.** On 2026-10-23 the Implementer asked three questions and proposed defaults; the Change Owner (Scott Wofford) replied: "proceed with the proposed defaults". The defaults, and where the Implementer had to supply one, are:
  1. **Model and tool, and budget.** The question named no default; the Implementer chose, and the Change Owner's reply is read as accepting it unless he says otherwise: both arms use the same candidate, `cursor-agent` with `--trust` and model `gpt-5.6-sol-high`, the tool and scope already authorized for the M1 and M2 attempts; the candidate cannot run commands, so the Implementer applies its returned diff in a clean workspace and runs the visible tests for it, identically in both arms. The budget is the pilot first; the Implementer reports the pilot's time and cost and the Change Owner decides whether to run the full round. A weak or strong candidate shifts both arms, so the report names the model and does not generalize beyond it.
  2. **What the AIDF arm's review consists of.** The minimum the framework requires for the task's class, not the extended rounds used to build the reference suite; the Change Owner's decision points are counted as each approval, reply or relay he is asked for.
  3. **Tasks.** All M1 positive cases with hidden tests and all three M3 cases of `suite-v2.json`; the five withdrawn cases and the negative M1 cases graded by disposition are excluded. The pilot uses one M1 case and one M3 case.
- **Invariants touched:** none. `core/02-authority.md` §3 (separation of duties) is applied to candidate and scorer (AC 8). `strategy/PHASE8-PROCESS-VALIDATION.md` §13's rules on missing data are reused.
- **Evidence strategy:** a pilot that exercises the scoring scripts on a known-good and a known-bad result per arm (counterfactual: the scripts must report the known-bad as worse); tests for the summary-table builder with synthetic runs; a recomputation of every table figure from the committed run records by an independent instance; the usual independent correctness review and a security pass over any script that executes candidate output.
- **Recovery / reversal approach:** purely additive. Reversal is a revert of the change; the evidence directories are standalone.
- **Known risks, disclosed:** (1) **Public answer key:** a model may have seen the reference application, which could inflate both arms equally and hide AIDF's effect; (2) **Small sample:** 3 runs per task per arm supports direction and size, not statistical proof; (3) **Single domain:** a small multi-tenant backend; (4) **Arm A's burden depends on how much review the Change Owner chooses to run**, and AIDF can look worse than it is if too much is run or better than it is if too little is run; AC 3 and AC 6 require the procedure to be recorded; (5) **Decision points are a rough proxy for attention**, not minutes, by the Change Owner's choice; (6) **AI scoring of judgment cases** (M3) is weaker than a mechanical check, which is why AC 8 blinds the scorer.
