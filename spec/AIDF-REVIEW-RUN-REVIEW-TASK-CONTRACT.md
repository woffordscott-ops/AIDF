# Task Contract: `verification/run_review.py`, the review-run tool

`core/01-lifecycle.md` §4. Class T2 with a security-focused review layer (see Classification); Approved status required from a human under Architect authority before implementation begins. **Status: Approved (2026-11-02; see Status).**

Source: item 5 of `strategy/AIDF-REVIEW-EFFICIENCY-PROPOSAL.md`; 5b of the split in `spec/AIDF-REVIEW-PREFLIGHT-TASK-CONTRACT.md` (5a merged as MR !62, the guarantee-sentences follow-up as MR !63). Evidence that the relay costs rounds and attention: in the last four changes the Implementer hand-built a prompt, a runner script and a throwaway checkout for every round (`Projects/verifier-prompt17.md` to `verifier-prompt23.md`, `run-verifier17.sh` to `run-verifier23.sh`); two reports were stored with the wrong line endings or a broken digest and had to be recommitted; round 2's report did not end in an Outcome line.

## Part A: Minimal

- **Intended outcome:** One command turns "the head to review" into a committed, byte-exact reviewer report, with the steps that went wrong by hand done by the tool: the head pinned to a full SHA, a throwaway clean checkout, the preflight run first, the reviewer started without the Implementer's credentials, the answer saved unmodified, its outcome line checked, and the report committed alone. The human still starts the reviewer: the Implementer's own session is denied the right to launch a reviewer agent (the auto-mode classifier, "Create Unsafe Agents"), and this contract does not ask to change that.
- **Acceptance criteria:**
  1. **Pinned head and clean checkout.** `run_review.py --head <ref> --previous <sha>` resolves `--head` to a full commit SHA and prints it; refuses when the working tree has uncommitted tracked changes or when the head is not an ancestor of `HEAD` of the repository it runs in; makes a throwaway clone of the repository (own object store and refs, not a `git worktree`, which shares refs with the origin repository) in a new empty directory outside the repository, checked out detached at that SHA. With `--previous` the delta command `git diff <previous> <head>` goes into the brief.
  2. **Preflight first.** It runs `verification/preflight.py` (arguments `--contract` and `--evidence`, as the preflight takes them) against the head before starting a reviewer, shows its output, attaches it to the brief, and does not start the reviewer if the preflight exits non-zero. `--skip-preflight <reason>` runs anyway and writes the skip and the reason into the brief and the log.
  3. **Brief.** The tool fills `templates/review-brief.md` from a brief file the Implementer prepares (`--brief`, with the round-specific checks in it) and adds a header the tool computes: the role and round, the full head SHA, the previous head and delta command, the base, the preflight output, the outcome words, and the path of the checkout. The brief is passed to the reviewer without shell interpretation (an argument list, never `shell=True`; on Windows a `.cmd` or `.bat` launcher receives the brief from a file or standard input and not as an argument, and the tool refuses a launcher that can only take it as an argument).
  4. **Reviewer environment.** The reviewer process receives an allowlist environment, not the caller's environment minus a list: the names the reviewer CLI needs to run (`PATH`, `SYSTEMROOT`, `TEMP`/`TMP`, `HOME`/`USERPROFILE`/`APPDATA`/`LOCALAPPDATA` as the default profile lists them) and the variables named with `--pass-env NAME` (for `cursor-agent`, `CURSOR_API_KEY` when the human uses a key). It drops every `GIT_*` variable, and sets the working directory to the checkout. The log and the screen show variable names, never values.
  5. **Reviewer run.** The default profile is `cursor-agent -p --output-format text --trust --force --sandbox enabled --model <model>` (flags read from `cursor-agent --help` on 2026-11-02; `--sandbox`, `--mode ask` and `--force` are the CLI's own). `--reviewer-command` replaces the profile. The tool starts the reviewer with a timeout (default 60 minutes), kills it on expiry, and records standard output and standard error separately, as bytes.
  6. **Verbatim answer.** The answer is the reviewer's standard output bytes, written to the report path with no change of line endings, encoding or whitespace, and the tool prints the file's SHA-256. The tool never edits, wraps or completes a report.
  7. **Outcome line.** The last non-empty line of the answer must be exactly `Outcome: PASS`, `Outcome: PASS_WITH_ADVISORIES` or `Outcome: BLOCKED`. If it is not, nothing is committed: the answer is kept in the output directory as `*.rejected`, the tool exits non-zero and says why. `--accept-nonconforming <reason>` commits it anyway, prints that this is a waiver of the Implementer's own rule and not of a review rule, and writes the reason into the log. (The round 2 report of `review-guarantee-sentences` would have been rejected.)
  8. **The checkout is unchanged.** After the reviewer exits the tool checks that the clone's `HEAD` is still the pinned SHA and that `git status --porcelain` is empty (ignoring nothing); otherwise the run is marked invalid, nothing is committed, and the changed paths are listed. It checks that the repository the tool was run in has the same `HEAD` and index as before.
  9. **Answer scan.** Before committing, the tool refuses an answer that contains the value of any environment variable of its own process whose name matches the secret pattern of the preflight (`token`, `proxy`, `password`, `secret`, `credential`, `api_key`, `ssh_`, `gitlab_`, `ci_`) and whose value is at least 8 characters, or of any variable named with `--pass-env`. It names the variable and never prints the value.
  10. **Report commit, alone.** The report path must match a report pattern in the `declared_scope` of the change's JSON contract; the tool commits only that path, with `core.autocrlf=false`, on top of the pinned head (it refuses if `HEAD` has moved), after checking that the blob in the commit has the SHA-256 of the answer bytes (so CRLF reports keep their digests), and that no other path is staged. It never pushes, never amends and never touches the dispositions file.
  11. **Log.** The tool writes start and end times (UTC), duration, model, head, previous head, exit status, outcome word, report SHA-256, the names of passed variables, and any skip or waiver reason to `<output directory>/review-run.json` and prints it. The log is not committed (the Implementer copies the numbers into the dispositions, as `human_time.py` expects).
  12. **Tests.** The reviewer in every test is a small Python script standing in for the CLI; no test starts a real reviewer. Each criterion has a test that fails without it: a dirty tree and a non-ancestor head are refused; the clone has its own refs (an `update-ref` inside it does not move the origin repository's branch); a failing preflight blocks the run and `--skip-preflight` records its reason; a stand-in reviewer prints its environment and shows that only the allowlist and the passed names arrive and that an inherited `GIT_ALLOW_PROTOCOL` and a token do not; a reply with CRLF endings is committed on a repository with `core.autocrlf=true` and the blob hash equals the answer hash; a reply with no Outcome line, and one with text after it, are rejected and are committed only with `--accept-nonconforming`; a reviewer that edits a file, moves the clone's `HEAD` or creates an untracked file makes the run invalid; a reply that contains the value of a secret variable is refused; a second staged path, a moved `HEAD`, a report path outside the declared scope and a timeout each stop the commit; the log has the listed fields. `mypy --strict` and `ruff` pass on the new file. `CHANGELOG.md` records the change as additive.
  13. **Scope.** No change to `verification/aidf_check.py`, `verification/phase2-task-contract.json`, `.gitlab-ci.yml`, `KERNEL.md`, trip-wires, `core/02-authority.md`, `core/05-review.md` or `verification/preflight.py` (the tool runs the preflight; it does not edit it).
  14. Outcome records (core/05-review.md section 6): the review report patterns are `verification/review-run-review-verifier-report*.md` and `verification/review-run-review-security-review-report*.md`; the dispositions file is `verification/review-run-review-verifier-dispositions.md`. This criterion only declares the paths.

  Spec Confidence: Clear at intake for criteria 1 to 11, Partial for criterion 5: the profile's flags come from the CLI's own help text and the tool cannot be tested against a real reviewer from the Implementer's session. The acceptance for that part is one real run started by the Change Owner after the tests pass (see Evidence strategy).

- **Declared scope:** `verification/run_review.py`, its tests under `verification/tests/` (`test_run_review.py`), `templates/review-brief.md` (a pointer to the tool), `CHANGELOG.md`, this contract, `verification/review-run-review-task-contract.json`, `verification/review-run-review-evidence-pack.json`, `verification/review-run-review-verifier-dispositions.md`, and the reports `verification/review-run-review-verifier-report*.md` and `verification/review-run-review-security-review-report*.md`. **Excluded:** everything named in criterion 13; launching a reviewer from the Implementer's session; pushing, merging or creating a merge request; reading or writing the dispositions; item 4 (trip-wire carve-out) and item 6 (adoption fixes); the cross-repository T3 change for the pending-criterion status.

## Part B: Plan

- **Approach:** Move the content of `run-verifier17.sh` to `run-verifier23.sh` (outside the repository, five variations of one script) into a single tool that takes the head, the brief and the model; reuse `verification/preflight.py` as a subprocess and its `SECRET_VARIABLE` pattern; commit with the sequence that worked for round 1 of `review-guarantee-sentences` (autocrlf off, blob hash check).
- **Invariants touched:** none of the stable surface. The tool starts no reviewer by itself and changes no review rule; the review layers remain as `core/05-review.md` sets them.
- **Evidence strategy:** counterfactual tests as in criterion 12, each mutation-checked as in the previous change (remove the control, the named test fails). Replay: run the tool with a stand-in reviewer over the heads of `review-guarantee-sentences` rounds 1 to 3 and show that the round 2 and round 3 reports of that change are rejected for the Outcome line, and that the round 1 report is committed with an equal blob hash on a repository with `core.autocrlf=true`. One real run: the Change Owner starts the tool with the real reviewer on the first Verifier round of this change's own review, or on a smaller throwaway head if he prefers; the result and the time are recorded. The tool is not used for the review that decides whether it is accepted until that run has passed.
- **Review budget (this change):** one pre-check with the preflight, two Verifier rounds and two rounds of the security-focused layer. A further round needs the Change Owner's recorded reason and a rank-1 finding in code, tests or security posture. Accepted limits, stated before review: (a) the tool does not contain the reviewer. A reviewer started with `--force` can run commands and read what the user account can read (other repositories, the profile, the network), and it needs the profile directories to use a stored login; the sandbox flag, the unchanged-checkout check and the answer scan reduce and detect, they do not prevent; (b) the environment allowlist is the tool's own list for one CLI, and a different CLI needs its own profile and its own review of that profile; (c) the answer scan finds only the values of variables the tool's process holds, not a secret the reviewer read from a file; (d) the outcome check reads one line and does not judge the report; (e) the tool cannot be tested against a real reviewer by the Implementer.
- **Protected files touched:** none.
- **Recovery / reversal approach:** `git revert`; the hand-run scripts still work; nothing else depends on the tool.

## Classification

Proposed **T2** with a security-focused review layer. The tool is a new verification tool in `verification/`, no kernel trip-wire. It starts a subprocess, assembles that process's environment, handles a credential name and writes a commit, so a second layer that attacks the environment, the argument passing and the commit path is proposed. (A Security Reviewer is a T3 role in `core/05-review.md` §1; for this T2 the layer would be a distinct reviewer instance given the security brief, and the Change Owner may instead require the change to be classified T3.)

## Decisions for the Change Owner

1. Approve as T2 with the security-focused layer (recommended), classify as T3, or drop the second layer?
2. The outcome check is strict (the last non-empty line must be the Outcome line; otherwise rejected unless `--accept-nonconforming`). Accept, or make it lenient (accept an Outcome line anywhere and report which)? Strict is recommended: the committed report is what the final-head binding and the dispositions rely on.
3. The preflight is run by the tool and a failure blocks the reviewer (criterion 2). Accept, or leave the preflight to the human as now?
4. The default profile covers only `cursor-agent`. Accept, or name another reviewer CLI that should be covered now?
5. Criterion 5 and the Evidence strategy ask you to start one real run yourself. Accept?
