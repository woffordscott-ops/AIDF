# Task Contract — Automatic, Cost-Aware Multi-Agent Task Routing

`core/01-lifecycle.md` §4. T2 — both parts required; Approved status required from a human under Architect authority before implementation begins.

## Part A — Minimal

- **Intended outcome:** Replace the manual, human-relayed handoff pattern this framework has used for every multi-agent task to date with three additive components: (1) an empirically-qualified specialty dimension on Layer 2 profiles, alongside the existing mode dimension; (2) a deterministic routing function that selects which qualified agent handles a given sub-task under a cost constraint; (3) a handoff-package generator that mechanizes the role-specific context curation `core/05-review.md` §2 already specifies in prose for Verifier/Security Reviewer, generalized to any declared role pair.
- **Acceptance criteria:**
  1. **Amended 2026-09-29, approved by Scott Wofford, Change Owner and Architect.** Original text: "`profiles/qualified/*.json` gains a `specialty` field, populated only through a suite-based, fail-closed, evidence-bound qualification mechanism matching the rigor already applied to `mode` — no self-reported or vendor-asserted specialty value is ever accepted." Superseded because implementation-phase investigation found direct modification of `profiles/qualified/*.json` actively blocked by two independent existing mechanisms in `verification/qualification_check.py`: its closed `PROFILE_FIELDS` allowlist would reject an added field outright, and `profile_payload_sha256` is computed over every field in the record, so adding one would invalidate the existing `review_bindings` attestations' own payload-hash cross-check. **Amended criterion:** specialty qualification is recorded as a separate, linked evidence record (`profiles/specialty/*.json`, referencing a `profile_id`) rather than a field added to the existing qualified-profile files. Each specialty record is populated only through a suite-based, fail-closed, evidence-bound qualification mechanism, cross-checked against the cited evidence's actual content (not merely its existence and digest) and against a real, resolvable Layer 2 qualified profile — no self-reported or vendor-asserted value is ever accepted. Independent review on 2026-09-29 (see Status) found the first implementation did not meet this bar; a rework pass (see Status) closed every code-level finding from both reviews and is pending re-review.
  2. A deterministic routing function (`verification/agent_routing_check.py`, matching the naming and fail-closed style of `verification/qualification_check.py`) that: (a) filters candidates to unexpired qualified profiles matching every existing Layer 2 assignment dimension plus the sub-task's declared hard-eligibility requirements (access/tooling); (b) ranks the eligible set by specialty-domain qualification evidence; (c) breaks ties by lowest cost without lowering required assurance; (d) applies the T2+ separation-of-duties exclusion as a final hard filter, run after ranking, never blended into the score — a selection that would violate it is rejected outright, never silently reassigned or overridden.
  3. A handoff-package generator that constructs the curated context slice for a target role per `modes/execution-modes.md`'s "Required context" column and `core/05-review.md` §2, generalized beyond the Verifier/Security-Reviewer pair it's currently specified for — provably excluding fields the target role must not receive (e.g., author rationale from a clean-room Verifier briefing).
  4. For any T2+ task, the router's role assignment is recorded **provisional** (Architect-declared, per the same pattern `modes/execution-modes.md` uses for mode declarations) rather than autonomously executed, until the stated graduation criterion in Part B is met.
  5. Positive and negative fixtures cover: correct routing under normal conditions; fail-closed rejection when no eligible candidate exists (never silently downgrade the requirement instead); fail-closed rejection when the only cost-optimal candidate would violate separation-of-duties (the function must select the next eligible candidate or fail closed — never override the exclusion); rejection of any specialty claim lacking suite-based qualification evidence.
  6. No change to `core/02-authority.md`, the `modes/execution-modes.md` mode contract, or any locked Layer 1 kernel content.

  Spec Confidence: Clear at intake via Spike (`spec/SPIKE-AGENT-ROUTING-PROPOSAL.md`, closed 2026-09-29).

- **Declared scope:** `profiles/**` schema and qualification mechanism; new `verification/agent_routing_check.py` and its fixtures/tests; new handoff-package generator and its fixtures/tests; narrowly required updates to `profiles/README.md` describing the specialty dimension. **Retroactively added 2026-09-29** (Codex review Finding F8 — these were committed in the first implementation pass without being named here): `metrics/change-observation.schema.json` and `metrics/observations/phase8-layer3-git-trust-hardening.json`, both load-bearing for acceptance criterion 1's content-verification. **Excluded:** the handoff transport mechanism itself (how one agent's structured output physically reaches another's input — separate follow-on, per the Spike's own scope boundary), any consumer/CI-policy repository change, `.gitlab-ci.yml` (governed separately, see Status), and anything in `core/` or `modes/`.

## Part B — Plan

- **Approach:** Build in dependency order — the `specialty` schema extension first (routing and handoff generation both depend on it existing), then the routing function with its fixtures, then the handoff-package generator with its fixtures. Each component gets its own fixtures and passes its own evidence floor before the next is built on top of it; nothing is integrated end-to-end until all three individually pass.
- **Invariants touched:** `core/02-authority.md` §3 (separation of duties) — not modified, but the implementation is the mechanical proof that it can be enforced automatically; `modes/execution-modes.md`'s declared-vs-qualified pattern — extended by direct analogy (provisional-vs-qualified specialty, provisional role assignment) but not altered. No locked-spec invariant is weakened.
- **Evidence strategy:** Counterfactual, same discipline used throughout the git-trust-boundary hardening this Spike was grounded in — construct a scenario where the cost-optimal candidate *would* violate separation-of-duties absent the exclusion filter, and prove the filter rejects that exact selection while accepting the next-best eligible one. Same pattern for the fail-closed cases: construct the "no eligible candidate" and "unqualified specialty claim" scenarios directly and prove rejection, not just absence of a positive case.
- **Recovery / reversal approach:** Purely additive — no existing routing exists today (every handoff this session was manual), so nothing depends on these components until they're deliberately invoked. Reversal is simply not integrating them; no rollback mechanism beyond ordinary revert is required.
- **Graduation criterion for provisional → qualified role assignment (T2+):** Twenty provisional, Architect-recorded routing assignments on T2+ tasks, audited with zero separation-of-duties violations and zero fail-closed routing errors, before autonomous (non-provisional) assignment is authorized for T2+ work. This number is a starting proposal for Change Owner approval, not a locked constant — revisit at the audit itself if the sample proves too small or too large to be informative.
