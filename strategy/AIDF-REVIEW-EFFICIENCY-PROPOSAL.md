# Proposal: fewer review rounds and less relay work, without lowering assurance (draft for the Change Owner)

**Status: draft; decisions recorded 2026-10-30 (see the last section). Nothing is built. It follows the Change Owner's request of 2026-10-30 to follow the order suggested after the four-model review (`SYNTHESIS.md` of that review, kept outside the repository).**

## Why

The project's own history (101 review reports, 56 merges, 675 branch commits; tables generated by script from git and the committed reports) shows:

- 8 of 14 reviewed changes went past the two-round cap of `core/05-review.md` §5, and 64 of the 101 reports were rounds beyond it. The base-app change took 27 Verifier and 8 Security rounds; the Stage 2 suite file 13 and 2.
- After the first rounds, almost every blocking finding was a sentence in an evidence pack or dispositions file (base app rounds 15 to 27). Each fix added new prose for the next round to fault.
- 71 of the 101 reports ended FAIL or BLOCKED, and 31 say FAIL, a word `core/05-review.md` §3 does not define.
- The first metric of `metrics/definitions.md`, human minutes per merged change, reads `unavailable` in both observation records.
- The measurement study (`strategy/AIDF-BENEFIT-BURDEN-REPORT.md`) found a pure rename in a permissions file escalated to T3 in 5 of 5 runs (4R, 4C).

Four independent models (Opus 5.5, GPT-5.6 Sol, Gemini 4 Argon, Kimi K3 Max), given the public tree and the tables, agreed on the first six points below. They are hypotheses until tested on the next changes.

## What would not change

Separated, adversarial review at T2 and T3; executable and counterfactual evidence; the jurisdiction rule; the nine trip-wires as they stand (item 4 asks for a decision, not a waiver); the rank-1 and rank-2 blocking rule for code, tests and security posture. Early review rounds found real defects (stale-token authority, races, double billing); this proposal does not touch them.

## Boundaries and budget for this change

Accepted limits, stated before any review (the practice item 1 would make routine): the proposal is advice until the Change Owner approves each change; the four-model review is a source of hypotheses, not a measurement; the finding-level replay of the old rounds is not built. Review budget: one pre-check, two Verifier rounds; a round beyond that needs the Change Owner's recorded reason and a rank-1 finding in code, tests or security posture.

## The changes, in the order suggested

1. **A stop rule with a menu** (`core/05-review.md` §5, `templates/task-contract.md`). The Task Contract declares a round budget (default T2: 2 Verifier; T3: 2 Verifier and 2 Security). When the last budgeted round is not PASS, the Change Owner chooses and records one of: merge with listed advisories; accept a named residual; split the change; stop; or one more round, allowed only if the last round found a rank-1 finding in code, tests or security posture. This replaces one authorization per round. *Open point found while writing:* §5 says accepted risk is for non-trip-wire residuals, and the public-export decision 8 accepted residuals on a trip-wire 4 change. The rule must say what a Change Owner may accept at T3 (a named, scoped residual with the reason) or the export decision must be re-read as a disclosed deviation.
2. **Records cannot block, and the pack is generated** (`core/05-review.md` §4 and §6, `templates/evidence-pack.md`, `verification/aidf_check.py`). A finding whose only subject is narrative, a count or history in an evidence pack or dispositions file is advisory and fixed by an append, with no new round, unless the sentence overstates a guarantee a consumer relies on. Counts, SHAs, command results and test names move into fields a script writes (`aidf_check.py pack`); review history is already barred from the pack. Why: base app rounds 15 to 27 and Stage 2 rounds 9 to 12.
3. **Measure the human** (`metrics/`, `templates/approval-request.md`). Every request to the Change Owner and every reply carries a UTC timestamp in the record; the metric is computed from them as an upper bound, with a manual active-minutes field. Cost: a field and a script. Why: no efficiency claim, including this proposal's, can be tested without it.
4. **Trip-wire 1 for changes a tool has verified as non-semantic** (`KERNEL.md`). *A decision for the Change Owner, and a kernel change (T3, with an ADR); not made here.* Option: a deterministic rename or formatting change with tool-verified references stays T0 on a trip-wire path, the verification is named in the contract, and anything unverifiable stays T3. Option: trip-wires apply to code that can reach production; fixtures and evaluation code get a recorded rationale and a check that shipping code does not import them. Risk: an agent calling a change "mechanical"; mitigated by naming the verifying tool and keeping the control cases `M0-TRANSFORM-01` and `M0-RENAME-02` to re-measure.
5. **Automate the relay** (new `verification/run_review.py`, a review-brief template). One command pins the head, builds a clean checkout, writes the brief from the contract (accepted limits, commands to run, token scrubbing, "list routes tried and closed"), runs the reviewer CLI, saves its answer verbatim, rejects an outcome word outside PASS, PASS_WITH_ADVISORIES, BLOCKED, commits the report alone, and logs start and end times. A tool in the verification directory, T2; it handles the environment, so it needs its own security look.
6. **Adoption fixes** (separate changes, mostly documents): README order (declared modes and T0 and T1 work first, qualification as an upgrade); one worked T1 and one worked T2 example; JSON templates and an `aidf_check.py init` for contracts (or parse the three inline lines); a repository map bound to a tree SHA instead of an inline listing capped at 128 KiB; a stated cold-start expectation and batch ratification for provisional patterns. Relaxing the Layer 2 identity tuple and expiry is a protocol change and a separate decision.
7. **The pending-criterion inconsistency** (`verification/aidf_check.py`). The criterion that declares outcome records stays `pending` in the Stage 2 pack until merge, but `validate_evidence` requires every criterion to be `passed` (the `pending` text check near line 454). Fix: a contract field that names outcome-record criteria, and an e4 status for them that the check accepts before merge and rejects after. T2 with tests.

## How we would know it worked

Baseline from the tables: median branch commits 3, 64 of 101 rounds past the cap, human minutes unknown. Over the next five T2 or T3 changes record rounds per change, rounds past the declared budget, commits per merge, authorizations and their timestamps, and findings by type (code, tests, record text, process). A change succeeds if rounds past budget fall to at most one per change with no rank-1 behaviour defect missed. A finding-level table of the 101 existing reports would allow a replay of items 1 and 2 on the old data; it is not built and needs the Change Owner's go-ahead.
